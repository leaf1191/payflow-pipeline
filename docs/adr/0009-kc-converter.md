# 0009. kafka connect converter 결정
## Context
parquet을 쓰기 위해서 스키마가 엄격하게 보장되어야 하는데(쓰기 단계), 이중 기존에 쓰던 json converter를 스키마 enable을 true로 하고 쓸지.
아예 avro converter로 전환할지 비교 결정 해야 함

## Decision
### OOM이 나는가?
avro는 레지스트리를 사용하며, json은 내부 캐시를 이용해도 무한정 저장하지 않음. 단 한도 초과시 캐시미스는 높아짐

### schema evolution을 지원하나?
avro는 스키마 에볼루션을 지원함. 반면 단순 json 컨버터는 저장하지 않음

### 스키마 파싱 비용이 큰가?
cdc 데이터 기준 동적 파싱 해야하므로 둘다 비슷하다고 판단됨

### 관리오버헤드가 있나?
avro는 스키마 레지스트리를 두어 관리. json은 없어도 됨

### 네트워크 대역폭 차이는?
avro는 바이너리에 스키마 id만 보내서 훨씬 적음. kafka 디스크 저장 효율도 높음

### parquet 호환차이는?
avro는 완벽히 호환, json는 데이터 에러 및 심하면 예외까지 뜰 가능성 존재

결론적으로
CDC 데이터인 만큼 스키마가 갑자기 확 바뀌지는 않으니 레지스트리 단에서 스키마 에볼루션은 크게 중요하지 않고(어짜피 웨어하우스는 snowflake에서 자체 에볼루션 관리함)
관리 오버헤드는 json이 유리, 처리속도도 k6 생산속도보다 뒤지지만 않으면 json이 나아보이지만, 호환성 문제가 치명적이라(protobuf도 같은 이유로 배제)
레지스트리를 두어 avro converter로 채택
단 레지스트리 HA는 본 프로젝트 밖의 영역이며, 우선순위도 낮아 스킵
