# 0005. S3 데이터 적재 ALO, EOS 비교

## Context
S3까지의 데이터 적재를 ALO 방식으로 처리할 것인지 EOS 방식으로 처리할 것인지 결정

## Decision
우선 디비지움 기준 ALO 방식을 적용하면 중간에 노드가 kill 되거나 좀비가 될 경우 오프셋 커밋이 이뤄지지 못하게 되고 그로 인해 중복데이터가 쌓일 가능성이 존재함(단 확실히 커밋된 오프셋 기준으로 읽어오니 유실 위험은 거의 없음)
EOS 방식의 경우 트랜잭션 코디네이터를 통해 작성할 때마다 트랜잭션을 생성하고, 오프셋 커밋도 매번 해야 함-> 성능이 느려짐
단 오프셋 커밋 전에 노드가 죽는다거나, 좀비가 쓴 데이터는 오프셋 커밋이 되지 않았으므로 전부 에포크가 바뀌면서 abort 됨 -> EOS가 보장

S3 Sink 기준 kafka에 쓰는 것이 아니므로 명시적인 방식은 없지만, 일반적으로 파일을 쓸 경우 오프셋 기준으로 파일명을 결정하므로, 동일한 오프셋을 써도 덮어쓰기가 가능함
다만 flush 타임아웃 주기 및 오프셋 커밋 주기 설정에 따라 flush 사이즈보다 작은 파일 2개가 만들어지면 두번째 파일은 덮어쓰기 안될 수가 있음
또한 좀비 노드의 경우 오프셋 커밋 주기 전에 새 워커가 새 데이터를 쓰고 좀비가 쓴 데이터가 네트워크 지연으로 늦게 도착하면 작은 세그먼트 파일이 역으로 덮어쓰기 될 수 있음-> 이 경우 S3 조건 설정이 필요

결과적으로 S3단에서 EOS를 보장하기엔 적재 성능이 느려지는데다(만약 평균 유입속도보다 느릴 경우 WAL로그 OOM 발생), 관리복잡도가 많이 올라감
무엇보다 snowflake에서 copy into시, 이미 처리한 파일 기준을 파일 명으로 판단하는데 이 경우 덮어쓰기 된 파일이 누락될 수 있음->snowflake 관리 복잡도도 추가로 올라감

하지만 결제 데이터를 기준으로 하는 만큼 데이터 중복은 필수적으로 피해야 하지만 snowflake merge 과정을 upsert를 이용하면 중복을 피한 채 훨씬 더 단순하게 처리할 수 있음. 이 경우 일부데이터에 대한 것이므로 컴퓨팅 비용도 크게 차이 없음(쿼리 짜기에 따라)
또한 copy into도 S3 파일명에 오프셋+시간으로 결정하면 덮어쓰기 대신 새 파일 생성되니 관리 오버헤드 없이 무손실로 copy into가 가능

따라서 관리 오버헤드가 낮고, 성능 떨어지는 것도 없는 ALO 방식으로 적재후 snowflake upsert로 중복 제거 설계로 결정
